Pet Passport — Project Context for Claude Code
What this is
A single hub app for pet needs: documents (with a real vault + scoped vet-sharing), vet care (in-clinic + virtual consultation booking, vet-side daily appointments), daily care coordination (caretakers), commerce (shopping, grooming, food/spa), a Paw Community feed, a Universal Pet ID, travel document checklists, and a QR emergency collar tag. Full spec in `PRD.md` — read it before starting new feature work.
Non-negotiable product principles

1. We are NOT an authority on travel/entry rules — we're a checklist. Every travel rules view must show a "last verified" date and a visible disclaimer to confirm with the airline/authority. Ruleset content itself (what's required, verification/refresh) is owned and maintained on the backend by ops — the app only renders it.
2. The QR tag's public emergency page must work with NO login and NO app install — plain mobile web page.
3. The QR emergency page must stay accessible even if the owner's subscription has lapsed. Never gate it behind billing status.
4. Medication reminders follow a three-step chain: vet prescribes (photo + dose + schedule) → owner confirms the prescription entry → caretaker administers per schedule and taps an explicit "confirmed given" action (timestamped, logged). A dismissed notification is never treated as confirmation. Caretaker reminders should not activate until the owner has confirmed the prescription.
5. Multi-pet support from day one — do not build single-pet-per-account assumptions into the data model.
6. Vet onboarding is manual for v1 — no automated credential-verification workflow to build. The trust signal on a vet profile reflects manual onboarding data only.

Stack

* Frontend: Next.js (App Router, TypeScript, Tailwind) — one web app serving three surfaces: owner/caretaker app under `(app)`, vet portal under `vet/`, and the public no-login QR page under `qr/[slug]`
* Backend/DB: Supabase (Postgres + auth + storage + RLS). Migrations, in order:
  - `0001_init.sql` — core schema
  - `0002_shop_and_community.sql` — adds `shop` order type + `community_posts`
  - `0003_pet_id_docshare_appointments.sql` — adds `pets.pet_code` (Universal Pet ID) + `document_shares`
  - `0004_fix_document_share_recursion.sql` — fixes an RLS recursion bug 0003 introduced (see gotcha below)
  - `0005_security_fixes.sql` — security review fixes: adds a missing `vet_bookings` SELECT policy for the vet themselves (they couldn't see their own appointments before this), and scopes all storage bucket write policies (and `documents` bucket reads) to `has_pet_access`/`document_shares`/vet status instead of "any authenticated user, any path"
  - `0006_travel_checklists.sql` — adds `travel_rulesets` (backend/ops-owned reference data, seeded with 5 sample airlines/countries) + `travel_checklist_progress` (per-pet fulfillment tracking) — closes a real PRD §3.2 scope gap that had never been built
  - `0007_security_fixes_round2.sql` — second security pass from a full-codebase review: (1) fixed the `documents` bucket's vet-share storage read policy, which joined `documents d on d.file_url = name` but never correlated `document_shares.document_id` back to `d.id` — any vet shared exactly one document could read every pet's documents; now reuses `is_shared_with_vet(uuid)` (0004) correctly. (2) Widened `profiles` RLS past the original self-only policy with three narrow, relationship-scoped read policies (vet profiles public, community post authors public, shared-pet relationship read) — the self-only policy silently broke every cross-user `profiles(...)` join: vet names always showed "Vetted professional", community posts always showed "Pet parent", and both medication-chain notification emails silently never sent. (3) Scoped `medication-photos` bucket writes to `has_pet_access`, matching the sibling buckets. (4) `medication_reminders: vet creates` now requires an explicit `caretaker_access` row with `role='vet'` instead of the role-agnostic `has_pet_access` — closes a gap where a plain caretaker could self-onboard as an unverified vet and prescribe for a pet they only had caretaker access to.
  - `0008_expanded_features.sql` — second feature batch: expanded `profiles` (`photo_url`, `dob`, `emergency_contact_*`) and `vets` (`designation`, `photo_url`, `species_focus[]`, `clinic_photos[]`, `clinic_address`, `amenities[]`); new `vet_reviews` (in-app only, one review per completed `vet_bookings` row); new `pet_care_routines` + `pet_care_routine_logs` (daily-ritual tracker, `has_pet_access`-scoped like `pet_weight_logs`); new `vet_has_booking_with_pet(uuid)` security-definer helper granting a vet read access to `medication_reminders`/`pet_care_routines`/`pet_care_routine_logs` for a pet they have any non-cancelled booking with (in addition to, not instead of, standing `has_pet_access`) — lets a vet review prescription history and the current care routine ahead of an appointment without needing standing `caretaker_access`; `vets` read policy widened from "any authenticated" to fully public (`using (true)`) and the `0007` vet-profile-public policy had its `auth.role() = 'authenticated'` condition dropped, both to support the new no-login `/clinics` directory; two new public-read storage buckets, `profile-photos` (path `${user_id}/...`) and `clinic-photos` (path `${vet_id}/...`).
  - `0009_meeting_links_and_travel_mode.sql` — `vet_bookings.meeting_url` (vet pastes an external call link — Zoom/Meet/etc — for a virtual consultation; no built-in video calling in v1, this is just a place for the owner to find the link); `vets.lat`/`lng` (self-reported clinic coordinates, no maps/places API involved); `pets.travel_mode_active`/`travel_destination` (owner-only on/off toggle, not date-range trip tracking). No RLS changes needed — existing policies on `vet_bookings`/`vets`/`pets` already cover updates to these columns.
  - `0010_qr_medication_visits_messaging.sql` — `medication_reminders` gains `owner_photo_urls[]`/`dose_times[]` (owner layers on more photos/structured "HH:MM" dose times after the vet's initial entry, without editing it) and `assigned_caretaker_id` (narrows who can mark a dose given — the `medication_confirmations: caretaker confirms` policy now also requires `assigned_caretaker_id is null or = auth.uid()`); new `vet_visit_notes` (vet remarks per pet/visit, `has_pet_access`-read, vet-write gated the same way as `vet_has_booking_with_pet`); new `pet_messages` (flat per-pet owner↔caretaker message log, `has_pet_access`-scoped, also emailed via `sendEmail` — the table is just the durable in-app record); `documents_type_check` constraint widened to add `'prescription'` so owners can upload their own scripts through the existing vault. No scheduler/cron exists in this app by design — `dose_times` drives a client-computed "due now / overdue" badge (`DueStatus.tsx`), never a pushed notification.
  - `0007` through `0010` are all applied to the live Supabase project as of this writing (verified via `pg_policies`/`information_schema` after each run, not just the SQL editor's "Success" message — see the gotcha below).
  - **Ambiguous embed gotcha**: `vets` has two foreign keys to `profiles` — `id` (the vet's own identity) and `onboarded_by` (who onboarded them). Any Supabase query that embeds `profiles(...)` through `vets` (directly, e.g. `vets.select("...profiles(full_name)")`, or nested, e.g. `vet_bookings.select("...vets(profiles(full_name))")`) must disambiguate with `profiles!vets_id_fkey(...)` or PostgREST rejects the whole query (`PGRST201`) and the caller's `data` comes back `null` — not a partial result, not a thrown error visible without checking `.error`, just silently empty. This is why the public clinic directory showed "No clinics onboarded yet" with a real row in the table. Grep `profiles!vets_id_fkey` for the fixed call sites (`src/lib/vets.ts`, `pets/[id]/page.tsx`, `pets/[id]/documents/page.tsx` ×2) before adding a new one.
* Email notifications: `src/lib/email.ts` wraps Resend. Two hooks in the medication chain — `createPrescription` (vet/pets/[id]/prescribe/actions.ts) emails the owner when a vet prescribes; `ownerConfirmPrescription` (pets/[id]/medications/actions.ts) emails every caretaker with `can_confirm_medication=true` once the owner confirms. Sending is best-effort (logs and swallows errors) so a failed email never blocks the actual DB write. **Sandbox limitation**: without a verified sending domain, Resend only delivers to the exact email the Resend account owner signed up with — not even `+alias` variants of it. Fine for solo dev testing, but real multi-user delivery (the actual point of this feature) needs a verified domain in Resend before it'll reach owners/caretakers who aren't that one account. Push notifications (in-app/mobile) are still not implemented at all.
* File storage: three Supabase Storage buckets — `pet-photos`, `medication-photos` (both public read, write scoped by policy), `documents` (private, read+write scoped by policy). All three buckets use the `${pet_id}/...` path convention so storage policies can check `has_pet_access` on the first path segment — keep that convention when adding new upload code.
* `next.config.ts` allowlists the Supabase project's hostname for `next/image` (derived from `NEXT_PUBLIC_SUPABASE_URL` at config load, not hardcoded). Without this, any `<Image src={supabaseStorageUrl}>` throws "Invalid src prop" at render time — this was a real latent bug that went unnoticed until the first prescription with a real photo actually rendered on the medications page. **Config changes here need a dev server restart** (`next dev` doesn't hot-reload `next.config.ts`) — if you add a new external image host, restart before assuming it's broken.
* Styling: no component library — design tokens + reusable classes (`.card`, `.btn-primary`/`.btn-secondary`/`.btn-ghost`, `.input`, `.badge-*`, `.page-title`, `.empty-state`, etc.) defined once in `src/app/globals.css` under `@layer components`. Warm/minimal palette via CSS custom properties (`--accent`, `--border`, `--success`, etc.), deliberately no `prefers-color-scheme` auto dark mode.

Running locally

1. Create a Supabase project, run all six migrations in `supabase/migrations/` **in order** against it (see the SQL editor gotcha below before you do)
2. Copy `.env.local.example` to `.env.local` and fill in the project URL, anon key, and service role key
3. `npm install && npm run dev`

Testing

* `npm run test:e2e` — Playwright critical-path suite (`tests/critical-paths.spec.ts`): login, pet creation + Universal Pet ID, public QR page reachable with zero auth, document upload, medications page, travel checklist. Runs against the real dev server and real Supabase project — no mocking — so it catches actual RLS/auth regressions, not just rendering bugs. `npm run test:e2e:ui` opens Playwright's UI mode for debugging.
* Tests reuse the existing confirmed test account (`tests/helpers.ts`) rather than signing up fresh, to skip email confirmation. Each run creates a new throwaway pet (`E2E Test Pet <timestamp>`) rather than depending on a fixed pet ID — cheap to leave lying around in a dev project, don't point this at production data.
* Gotcha hit while writing these: `page.waitForURL("**/pets/*")` also matches `/pets/new` itself (the page you start a create-pet flow on) and resolves before the real post-submit redirect happens. Use a pattern that excludes `new` explicitly, e.g. `/\/pets\/(?!new)[a-f0-9-]+$/`.

Route map

* `/` → public marketing landing page (`src/app/LandingPage.tsx`) for logged-out visitors; redirects straight to `/dashboard` for a logged-in session
* `/login`, `/signup` — Supabase email/password auth; both accept a `?next=<relative-path>` param (validated to start with `/` and not `//`, to rule out an open redirect) and land there after auth instead of the default `/dashboard` — used by the public "Book" CTAs below
* `/clinics`, `/clinics/[id]`, `/spa` — public, no-login browsing: vet/clinic directory (photo, designation, clinic photos, address, amenities, species focus, `vet_reviews` average) and a public grooming-tiers page. "Book"/"Contact" CTAs route through `/login?next=...` when logged out, straight to `/consultation`/`/grooming` when logged in. Reuses `getVetListings()` (`src/lib/vets.ts`) — it works both inside `(app)` and here, since `vets`/vet-profile/`vet_reviews` are all public-read (0008)
* `/dashboard`, `/pets/new`, `/pets/[id]` — owner/caretaker app (multi-pet)
* `/pets/[id]/caretakers/new` — owner grants caretaker/secondary_contact/vet access by email (caretaker must already have an account — no marketplace in v1)
* `/pets/[id]/medications` — medication chain UI: owner "Confirm prescription" button, caretaker "Confirmed given" button (both also enforced by RLS, not just UI)
* `/pets/[id]/routine` — daily care routine tracker (`pet_care_routines` + `pet_care_routine_logs`); owner/caretaker add routines and check off one completion per day per routine (`unique(routine_id, completed_on)`); "today" is resolved client-side (`RoutineList.tsx`) so it matches the caretaker's own timezone, same reasoning as the vet dashboard's day-bucketing (see gotcha below)
* `/profile` — any authenticated user's own profile: name, DOB, phone, photo, and the emergency-contact fields the SOS button (`src/components/SOSButton.tsx`, in the `(app)` header) emails on trigger via `sendSOS` (`profile/actions.ts` → `sosAlertEmail`, `src/lib/email.ts`)
* `/caretaker` — the scoped-down caretaker view: today's medication (due-status badge, "Confirmed given"), that day's routine check-offs (reuses `RoutineList.tsx` from `/pets/[id]/routine`), and a "Message owner" action per pet (`pet_messages` table + email, `MessageOwnerForm.tsx`). Deliberately narrow — full pet management (documents, travel, sharing, delete) stays on the regular pet page, reachable from here via the pet name link. Redirects to `/dashboard` if the viewer isn't an active caretaker on anything (same empty-state pattern as `/traveling`); the "My Tasks" nav link (`(app)/layout.tsx`) only appears when they are
* `/vet/onboard`, `/vet/dashboard`, `/vet/pets/[id]/prescribe`, `/vet/pets/[id]/patient` — vet portal; manual self-entered profile (now including designation/photo/clinic photos/address/amenities/species focus), prescribe requires the owner to have granted `role='vet'` access first. `/patient` is the appointment-time view — documents this vet was shared (`document_shares`), prescription history, and the pet's care routine, all readable once the vet has any non-cancelled `vet_bookings` row for that pet (`vet_has_booking_with_pet`, 0008) even without standing access
* `/qr/[slug]` — public emergency page, reads via the service-role admin client, never checks `subscriptions`
* `/consultation`, `/virtual-consultation` — browse onboarded vets + book (`vet_bookings`, type `in_person`/`virtual`); share `BookingForm` (`src/components/BookingForm.tsx`) and `getVetListings()` (`src/lib/vets.ts`) — no prior caretaker_access grant required to book. If the signed-in user has zero pets, `BookingForm`/`GroomingForm` show an inline "add your pet" mini-form (`createPetInline`, `pets/new/actions.ts` — same creation logic as `createPet` but returns the pet instead of redirecting) so a first-time booking doesn't detour through a separate page. Once a virtual booking exists, the vet pastes an external call link on their dashboard (`BookingsList.tsx`'s `MeetingLinkControl`, `meeting_url`, 0009) and the owner sees a "Join call" link on the pet's Vet bookings list — no built-in video calling
* `/grooming` — service tiers + booking creates an `orders` row (type `spa`)
* `/shop` — static curated catalog + "Add to order" creates an `orders` row (type `shop`) — no real inventory/payment
* `/community` — Paw Community feed; any authenticated user reads all posts, writes only their own (optionally tagged to a pet they have access to)
* `/pets/[id]/documents` — document vault: upload (private bucket, signed URLs generated per view, batched via `createSignedUrls` not one call per doc), and "Share with vet" scoped to a specific upcoming `vet_bookings` row (creates a `document_shares` row, not standing access)
* `/pets/[id]/travel` — travel document checklist: owner picks one airline and/or one destination country from a selector (`TravelSelector.tsx`) and only that ruleset's checklist renders — nothing shown until something's picked. Rulesets are backend/ops-owned reference data (`travel_rulesets`, currently 5 seeded rows, single-destination only — there's no "traveling from X" modeled, just destination); owner checks off which required documents they've handled (`travel_checklist_progress`) — app never fills or submits anything. Owner can also flip "traveling mode" on here (`pets.travel_mode_active`/`travel_destination`, 0009) — while on, `/traveling` shows up in the `(app)` nav for owner and caretaker alike
* `/traveling` — nearby vets while a pet's traveling mode is on; distance is Haversine, computed client-side (`NearbyVets.tsx`) between the visitor's browser geolocation and each vet's self-reported `lat`/`lng` (set on `/vet/onboard`, no external maps/places API). Redirects to `/dashboard` if nothing's actually traveling. Grooming/shop vendors aren't real location-backed entities yet, so this only covers vets for now
* Pet photo: optional upload on `/pets/new` (uploaded server-side, after the pets-row insert, since the `pet-photos` write policy needs `has_pet_access` on an id that has to already exist); shown on the dashboard, pet detail page, and caretaker list wherever `photo_url` is set
* Delete pet: a ✕ on each dashboard card (native `confirm()`, `QuickDeleteButton.tsx`) and a two-step inline confirm on the pet detail page (`DeletePetButton.tsx`) — both call `deletePet` (`pets/[id]/actions.ts`), owner-only, cascades to every pet-scoped table via existing `on delete cascade` FKs (does not clean up orphaned Storage objects — pre-existing gap, not new)
* All four booking/ordering pages share `getAccessiblePets()` (`src/lib/pets.ts`) for the "which pet is this for" selector; the pet detail page also lists that pet's `vet_bookings` history directly (booking/medical history reachable any time, not just implied by the data existing)

Role-based interface (one app, routed by role — not separate codebases)
* `(app)/*` — owner + caretaker interface. `/dashboard` splits into "Your pets" (owner, full admin) and "Pets you care for" (caretaker — today's owner-confirmed medications with an inline "Confirm given" button, no need to drill into the pet page)
* `vet/*` — doctor interface. `/vet/dashboard` is appointments-first: today's `vet_bookings` with confirm/mark-done actions, "Patients with standing access" (via `caretaker_access` role=`vet`) is secondary
* New-user onboarding: signup → if the account ends up with zero owned/caretaker pets, `/dashboard` redirects to `/pets/new?onboarding=1` (species/breed/DOB, tailored copy, "Skip for now"). Signup itself has an "I'm joining as someone else's caretaker" checkbox that skips straight to `/dashboard` instead.

Security notes

* File uploads from client components (document vault, medication photos) always write to `${pet_id}/...` paths — the storage RLS policies (0005) key off the first path segment via `has_pet_access(split_part(name, '/', 1)::uuid)`. Any new upload feature must follow the same convention or the storage policy needs a matching update.
* Every server action re-checks `auth.getUser()` and relies on RLS as the actual enforcement layer (not just the UI) — this held up well in review; keep it when adding new actions rather than trusting a client-supplied ID.
* Accepted risk, not fixed: `inviteCaretaker` (`src/app/(app)/pets/[id]/caretakers/new/actions.ts`) reveals whether an email has a Pet Passport account via its error message ("No account found..."). This is deliberate UX (the owner needs to know the invite won't land) but is a mild user-enumeration surface — revisit if it becomes a real concern.
* `orderProduct`/`bookGrooming` accept client-supplied product name/price/service strings with no server-side catalog validation — fine given there's no real payment processing in v1 (PRD §6), but don't build real commerce on top of this without adding a server-side source of truth for pricing.

Conventions

* Server Actions (`actions.ts` next to the page that uses them) for all writes; RLS in the migration is the actual enforcement layer, the UI is a convenience on top
* `requireUser()` (`src/lib/supabase/server.ts`) is the shared auth guard — every server action and protected layout calls it instead of hand-rolling `createClient()` + `auth.getUser()` + `if (!user) redirect("/login")`. Returns `{ supabase, user }`. Some server components (e.g. dashboard, medications page) intentionally still call `createClient()` + a local null-check with a different fallback (`notFound()`, `return null`) instead — that's deliberate defense-in-depth under a layout that already guards the route, not an inconsistency to "fix" by swapping in `requireUser()`.
* `one<T>()` (`src/lib/supabase/relations.ts`) normalizes a Supabase joined to-one relation (`T | T[] | null`) to `T | null` — use it instead of re-writing `Array.isArray(x) ? x[0] : x` at each call site.
* The public QR page filters secondary contacts by `finder_may_call`/`vet_may_call` before rendering (not just in the caption) — a contact with both flags false must never appear on that page at all.
* Photo uploads (`profile-photos`, `clinic-photos` buckets, added 0008) follow the same client-uploads-then-calls-server-action pattern as `documents`/`medication-photos`: a client component uploads via the browser Supabase client, gets a public URL, and passes that URL into the server action — never upload from inside a server action itself. New/edited vet or profile photos are deliberately additive (existing `clinic_photos` are merged with, not replaced by, new uploads on each save — see `onboardVet`).
* New/edited photo `<img>` tags in this batch (`ProfileForm`, clinic directory/detail pages, caretaker list) intentionally use a plain `<img>` with an eslint-disable comment rather than `next/image`, since these are variably-sized user photos with no fixed dimensions — this is a deliberate deviation from the `next/image` pattern used for pet/medication photos elsewhere (see the `next.config.ts` allowlist note above), not an oversight.
* "Today" for anything date-bucketed in the UI (vet dashboard appointments, routine check-offs) must be resolved **client-side**, never in a Server Component — `new Date()` in a Server Component resolves in the server process's timezone, not the viewer's. See `BookingsList.tsx` and `RoutineList.tsx` for the pattern (a small `"use client"` component that receives server-fetched data as props and does its own local-date math).
* **Client components that read `new Date()`, `navigator`, or anything else environment-dependent must not branch on it in the initial render.** Next.js server-renders client components too, and the server has no `navigator`/real client clock — computing a value that differs between server and client (even in a lazy `useState` initializer) throws a hydration-mismatch error and the whole subtree re-renders from scratch. Fix: initialize state to the same neutral value on both sides (e.g. `"locating"`, `null`), then compute the real value inside a `useEffect` after mount — see `NearbyVets.tsx` (geolocation) and `DueStatus.tsx` (dose-time due/overdue) for the pattern. Relatedly, `react-hooks/set-state-in-effect` forbids calling `setState` synchronously in the effect body when there's no async boundary (no promise, no event callback) — defer with `setTimeout(fn, 0)` (with the matching `clearTimeout` cleanup) rather than calling it directly, same two files for the pattern.
* `src/lib/supabase/client.ts` (browser), `server.ts` (Server Components/Actions, cookie-based session), `admin.ts` (service role, server-only, currently only used by the QR page) — don't cross these
* No git repo yet by request — initialize when ready
* Client form components: capture `e.currentTarget` into a local variable *before* any `await` in the submit handler. The DOM nulls out `currentTarget` once event dispatch finishes, so `e.currentTarget.reset()` after an awaited server action throws — do `const form = e.currentTarget` first, then `form.reset()`.
* Insert-then-`.select()` (i.e. `INSERT ... RETURNING`) can spuriously fail with an RLS violation when the SELECT policy calls a `SECURITY DEFINER` function that queries the same table mid-statement — even when the row's own data clearly satisfies the policy. Symptom: the same insert succeeds without `.select()`/`RETURNING`, and a separate follow-up `SELECT` can see the row fine. Workaround used throughout: generate the row's `id` client-side (`randomUUID()`) and do a plain `.insert()` with no `.select()`.
* **RLS recursion between two tables**: if table A's policy queries table B, and table B's policy queries back into table A (e.g. `documents` ↔ `document_shares` in 0003/0004), Postgres throws `42P17 infinite recursion detected in policy`. Fix by wrapping the cross-table check in a `SECURITY DEFINER` `stable` SQL function (same pattern as `has_pet_access`) — the function's internal query runs with the definer's privileges and doesn't re-trigger the other table's RLS, breaking the cycle. Don't write a policy with a raw correlated subquery into a table that itself has RLS referencing back — always ask "could this cycle?" before adding a cross-table policy.
* **The Supabase SQL editor is not reliable for multi-statement scripts in this environment.** Across this project, pasting a multi-statement migration has repeatedly shown "Success. No rows returned" while some or all of the statements silently did not apply (verified via direct REST calls against `information_schema` / the actual table afterward) — root cause never fully pinned down (possibly a stale/reused editor tab, possibly something else), but it's happened enough times to treat as expected. When running a new migration: (1) always use a genuinely fresh "+ New query" tab, never reuse one, (2) if a multi-statement script is going to run, verify the result afterward via a direct `curl` against `${NEXT_PUBLIC_SUPABASE_URL}/rest/v1/<table>` with the service-role key rather than trusting the editor's "Success" message, (3) if verification shows it didn't apply, re-run in smaller chunks (a few statements at a time, verifying after each) rather than re-pasting the same full script — that has reliably worked every time this came up, where re-running the identical full script repeatedly did not.

Explicitly out of scope for v1

* Auto-filling/submitting official travel or customs paperwork
* Insurance claims processing
* Pet-sitter/walker marketplace
* GPS pet tracking (QR tag is static info only)
* Automated travel ruleset verification (backend/ops-owned)
* Automated vet credential verification (manual onboarding only)
